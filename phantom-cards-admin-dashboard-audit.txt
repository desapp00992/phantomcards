1. PROJECT OVERVIEW

Architecture
------------

The project is a small custom Node.js application with two runtime services:

1. Site A - user marketplace and account service
2. Site B - isolated Paystack payment service

Frameworks and infrastructure
-----------------------------

- Frontend: plain HTML, CSS, and browser JavaScript
- Backend: native Node.js http server
- Database: JSON files on disk
- ORM/query layer: none
- Payment provider: Paystack through raw HTTP requests using fetch
- Authentication: custom password hashing and cookie-backed sessions
- Frontend state: in-memory browser state hydrated from /api/state

There is no React, Vue, Next.js, Express, Fastify, Prisma, Sequelize, PostgreSQL, MySQL, MongoDB, or other formal framework/database layer.

Runtime architecture
--------------------

Site A:

    Browser
      |
      v
    Site A: server.js
      |
      v
    data/phantom-cards.json

Site B:

    Site A
      | signed HMAC request
      v
    Site B: payment-service/server.js
      |
      v
    Paystack
      | webhook / verification
      v
    Site B
      | signed HMAC callback
      v
    Site A

Site A runs on port 3000 by default. Site B runs on port 4000 by default.

The README describes using HTTPS tunnels such as Cloudflare Tunnel for browser and Paystack testing. No production hosting, deployment manifests, containers, process manager, CI/CD configuration, or backup system is present.

Deployment details are therefore: NOT CLEAR FROM CURRENT IMPLEMENTATION.

Main files
----------

- index.html - user-facing application markup, styling, legacy inline frontend code, navigation, and page shells
- app.js - active frontend API bridge and current persisted-product flows
- server.js - Site A backend, authentication, cards, balances, purchases, redemptions, withdrawals, KYC, and internal payment callbacks
- payment-service/server.js - Site B Paystack initialization, verification, webhook handling, and callbacks
- payment-config.js - hardcoded allowed Paystack payment emails
- data/phantom-cards.json - Site A data store
- payment-service/data/payment-service.json - Site B data store
- data/kyc-documents/ - binary KYC document storage
- test/ - Site A tests
- payment-service/test/ - Site B tests

4. USER ACCOUNT SYSTEM

Registration
------------

Endpoint: POST /api/auth/signup

Required:

- Name
- Mobile number
- Password

Optional:

- Gmail address

Validation:

- Mobile must match 0\\d{9}
- Email must be Gmail if supplied
- Password must be at least six characters
- Phone must be unique
- Email must be unique when supplied

The user is created with a random usr_ ID, scrypt password hash, zero balances, NOT_VERIFIED KYC status, no PIN, an assigned Paystack email, and an active session.

User ID format
--------------

usr_<18 hexadecimal characters>

Login
-----

POST /api/auth/login accepts either email or mobile number and validates the password against the scrypt hash.

Sessions
--------

Authentication uses a phantom_session cookie containing a random 64-character hexadecimal token.

Cookie attributes:

- HttpOnly
- SameSite=Lax
- Path=/
- Max-Age=30 days
- Secure when the request is detected as HTTPS

Sessions are stored in the JSON database. There is no separate authentication server.

Password reset
--------------

POST /api/auth/forgot and POST /api/auth/reset create and consume hashed reset tokens.

In non-production, the forgot endpoint returns the reset token directly because no mail provider is configured.

Assigned Paystack email
-----------------------

The only allowed Paystack payment emails are:

- danny700218+1@gmail.com
- danny700218+2@gmail.com

Assignment is round-robin based on the number of users when they register. The assigned value is stored permanently on the user.

The actual user email and Paystack checkout email are separate. The actual email is used for account contact/login. The assigned Paystack email is used for Paystack checkout.

Account status and verification
-------------------------------

There is no general account-status field. KYC state and PIN existence are the main account-state indicators.

KYC statuses:

- NOT_VERIFIED
- PENDING
- VERIFIED
- REJECTED

The frontend displays a user as Active unless KYC is rejected.

There is no suspended, banned, closed, email-verified, phone-verified, role, or permission state.

An admin would realistically need user ID, name, phone, actual email, assigned Paystack email, registration date, last activity, balances, KYC history, purchase count/value, redemption count/value, withdrawal history, deposit history, session/security information, and account restrictions. Only some exist now.


5. CARD SYSTEM

Card creation
-------------

Cards are generated by makeCards() in server.js. The initial catalog contains 80 deterministic product records.

Categories:

- Digital
- Gaming
- Crypto
- Collectible
- Access
- Exclusive
- Limited
- Rare

Prices are stored in GHS. Display USD is calculated using a fixed GHS 12 per USD conversion.

Inventory
---------

Each card has stock and active. active is recalculated as stock > 0 during catalog synchronization. Purchases decrement stock and set active false when stock reaches zero.

There is no separate inventory-item table, inventory movement history, admin card creation API, or explicit pause flag. Because active is derived from stock, manually pausing a card is not currently supported reliably.

Ownership and lifecycle
-----------------------

A purchased card is represented by a purchase and a code record linked through userId, cardId, purchaseId, and orderId.

Purchases normally start as sealed. The code status changes from unused to redeemed. The purchase status itself generally remains sealed.

Codes are generated as two uppercase letters plus twelve uppercase alphanumeric characters. Codes are stored in plaintext.

Card expiration
---------------

There is no expiration field, expiry date, or expiration process. NOT CLEAR FROM CURRENT IMPLEMENTATION whether expiration was intended.

Reward multiplier
-----------------

Current backend range: 3.52x to 4.42x.

The reward is selected during purchase and stored on purchase and code records. The final reward amount is purchase amount multiplied by the selected multiplier.

Historical records contain older multipliers. The migration preserves historical reward snapshots. Unused legacy codes with invalid old multipliers can be recalculated at redemption; completed redemptions are not rewritten.

Frontend responsibility
----------------------

The frontend displays the server-provided reward range and does not calculate the final reward. The backend is authoritative.

Admin card requirements
----------------------

An admin would need catalog, pricing, reward configuration, stock, sold count, redemption count, unredeemed-code count, reward liability, restocking, pausing, and audit/versioning. These capabilities do not currently exist.


6. REWARD SYSTEM

Current range: 3.52x to 4.42x.

The range is defined in server.js through REWARD_MULTIPLIER_MIN, REWARD_MULTIPLIER_MAX, and REWARD_BANDS.

Formula:

    rewardAmount = purchaseAmountGhs * selectedMultiplier

The result is rounded to two decimal places.

The reward is allocated during POST /api/purchases and persisted to purchase and code records. It is credited only during POST /api/redemptions.

Completed redemptions are historical snapshots and are not rewritten. There is no admin reward-adjustment API.

The frontend displays the potential range before purchase and the final reward after redemption. It does not control the financial calculation.

An admin should monitor multiplier distribution, total purchased value, total redeemed reward value, unredeemed liability, reward-to-purchase ratios, and historical versus current configurations.


7. WALLET / BALANCE SYSTEM

WALLET BALANCE
--------------

Field: users.walletBalance

Purpose: funds card purchases.

Money enters through successful wallet top-ups. Legacy/test records may also credit it directly.

Money leaves through card purchases.

It cannot be withdrawn.

WALLET BALANCE transactions use account=wallet.

REDEEMED BALANCE
----------------

Field: users.redeemedBalance

Purpose: holds redemption rewards and funds withdrawals.

Money enters through successful redemptions and rejected-withdrawal restoration.

Money leaves through withdrawal holds.

REDEEMED BALANCE transactions use account=redeemed.

EXTERNAL ACCOUNT
----------------

Used for the GHS 70 bypass fee and GHS 70 refund. External transactions do not affect either user balance.

Important balance behavior
--------------------------

A withdrawal request immediately deducts the requested amount from Redeemed Balance. If rejected, the requested amount is returned directly to the balance, but there is no separate balance-credit transaction.

normalizeDb() rebuilds balances from qualifying transactions, which is complex and status-dependent. There is no formal ledger or balance snapshot history.


8. TOP-UP / PAYSTACK SYSTEM

User entry point
----------------

Frontend: app.js -> POST /api/deposits
Backend: server.js -> POST /api/deposits

The frontend offers preset amounts from GHS 30 to GHS 500. The backend accepts any amount of at least GHS 30.

Site A top-up flow
------------------

1. Authenticate user
2. Validate amount
3. Capture Gmail contact email if missing
4. Create pending deposit record
5. Generate unique Site A transaction ID
6. Generate deposit reference
7. Set expiry, normally 15 minutes
8. Send signed request to Site B

Site A to Site B authentication uses Bearer secret, request ID, timestamp, and HMAC-SHA256 over timestamp.requestId.rawJson.

Site B initialization
---------------------

POST /api/v1/payments/initialize validates the request, calls Site A internal lookup, reconciles user/amount/currency/purpose/customer email, creates a Paystack transaction, stores it, and returns an authorization URL.

Paystack customer email is always one of the two hardcoded allowed emails and is not the user’s actual email.

Paystack metadata contains site, Site A transaction ID, Site A user ID, and purpose.

Paystack webhook
----------------

POST /api/v1/webhooks/paystack validates raw-body HMAC-SHA512 using PAYSTACK_SECRET_KEY. It checks event ID duplication, reference, amount, currency, metadata, Site A IDs, and purpose.

Relevant events are charge.success and charge.failed. Other event types do not appear to update payment status.

Site B to Site A callback
-------------------------

Wallet callback: POST /api/v1/webhooks/payment-status.

Site A only credits Wallet Balance after a reconciled SUCCESS callback.

Wallet credit creates a wallet transaction and deposit receipt and is protected by terminal status/reference checks and callback IDs.

Multiple attempts
-----------------

Every top-up creates a new attempt. Multiple attempts for the same amount are allowed.

Potential weaknesses
--------------------

- No admin reconciliation interface
- Limited callback retry behavior
- No visible scheduled expiry/reconciliation worker
- Site B requestIds storage is not actively used for global replay protection
- Failed initialization can leave a pending Site A record
- Existing persisted deposit records use incompatible legacy fields/statuses

Frontend return mismatch
------------------------

Site B redirects using a wallet_topup query parameter containing the Site A transaction ID. app.js expects wallet_topup plus a separate transactionId parameter. Therefore browser confirmation can fail even when the webhook successfully credits the wallet.

Broken recovery flow
--------------------

The frontend calls POST /api/deposits/:reference/verify, but no such backend endpoint exists. The frontend labels the input as a Paystack reference, while the backend status endpoint expects a Site A transaction ID.


9. CARD PURCHASE SYSTEM

Entry point: POST /api/purchases.

The backend checks authentication, idempotency key, card availability, stock, minimum wallet balance, sufficient wallet balance, and the daily exact-price quota.

Card purchases use Wallet Balance and do not use Paystack.

The backend:

1. Debits Wallet Balance
2. Decrements stock
3. Updates active state
4. Creates purchase record
5. Updates daily purchase count
6. Generates code
7. Creates purchase transaction
8. Creates purchase receipt
9. Saves JSON

Each user may buy at most two cards per exact USD price per Ghana calendar day. Different cards with the same price share the same quota.

Purchase idempotency uses userId plus idempotencyKey. The frontend persists keys in localStorage, and the backend serializes purchase mutations within one process.

There is no cross-process protection, external card payment, or separate purchase fulfillment service.


10. REDEMPTION SYSTEM

Endpoint: POST /api/redemptions.

The backend normalizes and validates the code, finds it, verifies ownership, verifies unused status, resolves the purchase/card, resolves the reward snapshot, changes status to redeemed, sets redeemedAt, creates redemption reference, credits Redeemed Balance, and creates transaction and receipt.

A different user cannot redeem the code. A redeemed code cannot be redeemed again.

The frontend handles formatting, confirmation, and display. The backend owns all financial and ownership decisions.


11. WITHDRAWAL SYSTEM

Eligibility
-----------

The user must have at least three lifetime redeemed cards, a saved method, at least GHS 10 requested, sufficient Redeemed Balance, and a valid four-digit PIN.

There is no maximum withdrawal rule and no lifetime purchase-count requirement.

Fee
---

operationalCharge = requestedAmount * 10%
actualAmount = requestedAmount - operationalCharge

The full requested amount is deducted from Redeemed Balance. The record stores both requested and net amounts.

Methods
-------

MTN Mobile Money, Telecel Cash, and AT Cash are supported.

PIN
---

The first method creation sets the user PIN. Later method creation and withdrawal require the PIN. PINs are scrypt-hashed.

Statuses
--------

Unverified users begin at PENDING_KYC_VERIFICATION. Verified users begin at pending. Existing constants include approved, processing, completed, rejected, cancelled, and refunded, but not all transitions are implemented.

Admin approval
--------------

POST /api/admin/withdrawals/:reference/approve changes pending to approved and stores an admin note.

POST /api/admin/withdrawals/:reference/reject returns the requested amount to Redeemed Balance, changes the status to rejected, and stores an admin note.

There is no payout completion implementation in the current code. NOT CLEAR FROM CURRENT IMPLEMENTATION how existing completed records were finalized.

KYC
---

POST /api/kyc/submissions accepts exactly two JPEG, PNG, or PDF documents up to 5 MB each. Documents are stored as binary files under data/kyc-documents/<userId>/ and metadata is stored in one user.kycSubmission object.

POST /api/admin/users/:userId/kyc/verify sets the user to VERIFIED and releases all that user’s PENDING_KYC_VERIFICATION withdrawals to pending.

POST /api/admin/users/:userId/kyc/reject sets the user to REJECTED but does not automatically reject withdrawals, return held funds, or store a separate decision record.

Review timing of 24-72 business hours is frontend copy only. Backend SLA behavior is NOT CLEAR FROM CURRENT IMPLEMENTATION.

GHS 70 bypass
-------------

The bypass creates a kycBypassPayment, initializes a Paystack checkout through Site B, and waits for a signed callback.

Successful callback:

- Sets payment status to success
- Marks withdrawal kycBypassUsed
- Sets fee to GHS 70
- Sets paymentStatus to success
- Changes withdrawal to approved
- Sets autoApprovedReason to kyc_bypass_fee_paid

The account remains NOT_VERIFIED or otherwise unchanged from a KYC perspective.

Refund
------

Successful bypass creates an external GHS 70 debit and a separate external GHS 70 refund. The refund is represented in withdrawal history, transactions, and receipts. It does not credit Redeemed Balance.

Original withdrawal and refund are linked through IDs and references.


12. TRANSACTION SYSTEM

Multiple financial systems exist rather than one complete accounting model.

Unified Site A transactions
---------------------------

- Wallet top-up: credit, wallet account
- Card purchase: debit, wallet account
- Redeemed code: credit, redeemed account
- Withdrawal: debit, redeemed account
- KYC bypass fee: debit, external account
- KYC Fee Refund: credit, external account, REFUND entry type

Purchase transactions link through cardId and orderId. Redemption transactions link through cardId, orderId, purchase amount, reward amount, and multiplier. Withdrawal transactions link through withdrawalId and methodId. Refund transactions link through original withdrawal and payment references.

Receipts duplicate transaction data. Deposits, purchases, withdrawals, codes, KYC payments, and Site B transactions are separate source records joined by string references.

There is no true unified accounting model, no double-entry ledger, no balance-after field, no status-transition history, and no payout-provider transaction model.

Rejected withdrawals return funds directly without creating a separate reversal transaction.

17. IMPORTANT ARCHITECTURAL RISKS

1. Flat-file persistence: all Site A data is one JSON document with no transactions, indexes, locking, or safe multi-instance behavior.

2. Only purchase mutations are explicitly serialized. Redemptions, withdrawals, KYC actions, admin changes, and payment callbacks do not use the same mutation queue.

3. No relational integrity. Records can become orphaned because IDs are only strings.

4. Multiple financial systems. Direct balances, transactions, receipts, deposits, purchases, withdrawals, KYC payments, and Site B payment records are not one accounting system.

5. Rejected withdrawals lack a reversal transaction. Funds are returned directly to the balance and only metadata indicates the return.

6. Status inconsistency. The system mixes uppercase, lowercase, and legacy statuses such as SUCCESS/success and PAYMENT_INITIALIZED/initialized.

7. Historical reward inconsistency. Existing multipliers differ from the current 3.52-4.42 range, requiring historical/current distinction.

8. Hardcoded business rules. Paystack emails, exchange rate, reward range, fees, limits, and thresholds are embedded in code.

9. Weak admin authorization. One shared static token provides no identity, roles, MFA, or action ownership.

10. The current admin token is not configured in the repository’s current .env.

11. No KYC document access layer. Files exist but no secure admin retrieval endpoint exists.

12. No KYC decision history. A single mutable user.kycSubmission object can be overwritten.

13. No payout completion flow. processing/completed/cancelled are not fully implemented.

14. Payment callback replay handling is incomplete. Per-payment callback IDs exist, but Site B global request ID storage is not actively enforced.

15. Payment retry behavior is limited. No visible scheduled callback retry/reconciliation worker exists.

16. Top-up browser return mismatch. Site B and app.js expect different query parameter formats.

17. Broken deposit recovery endpoint. The frontend calls an endpoint that does not exist and uses a different reference concept than the backend.

18. Duplicate frontend implementations. index.html contains old mock flows while app.js contains current API-backed flows.

19. Sensitive plaintext values exist in JSON, including session tokens, redemption codes, payment references, and withdrawal details.

20. No complete audit trail exists for administrative actions.
