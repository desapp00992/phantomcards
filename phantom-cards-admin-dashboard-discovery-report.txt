PHANTOM CARDS — ADMIN DASHBOARD DISCOVERY REPORT
================================================

Audit scope
-----------

This is a read-only technical audit of the existing PHANTOM CARDS project.
No admin dashboard was built. No project files, database files, migrations,
authentication logic, payment logic, card logic, redemption logic, or
withdrawal logic were modified during the audit.


A. PROJECT STACK
----------------

FACT FOUND IN PROJECT

- Frontend: plain HTML, inline CSS, and browser JavaScript.
- Backend: custom Node.js http.createServer() implementation.
- No Express, Fastify, NestJS, Next.js, or other backend framework exists.
- Database: JSON files on disk.
- ORM/query layer: none.
- Site A owns the marketplace, users, balances, cards, redemptions, KYC,
  and withdrawals. It runs on port 3000 by default.
- Site B is an isolated payment service that owns the Paystack secret. It
  runs on port 4000 by default.
- Payment provider: Paystack through native fetch calls.
- Authentication: custom password hashing with Node crypto.scrypt, session
  records stored in JSON, and an HttpOnly cookie.
- Authorization: user session checks plus a separate environment-token
  mechanism for a small number of admin actions.
- Package dependencies: effectively none. package-lock.json contains no
  application dependencies.
- Migrations: none.
- Background jobs: no worker, queue, cron process, or scheduler exists.
- The frontend performs periodic background refreshes every three seconds.
- Logging uses console.log, console.warn, and console.error.
- No persistent logging system exists.
- Tests use Node's built-in test runner.
- Current tests passed:
  - Site A: 9 tests passed.
  - Site B: 3 tests passed.

Relevant files:

- server.js
- app.js
- index.html
- payment-service/server.js
- payment-config.js
- README.md

RECOMMENDATION / INFERENCE

The future admin system should initially preserve the Site A/Site B
separation. Site B must remain the only service that communicates with
Paystack using the secret key.

The current JSON persistence layer is suitable for a prototype but is not a
safe long-term foundation for concurrent administrative operations, financial
reconciliation, reporting, or audit history.

Card marketplace:

- Frontend: Shop page, product grid, search/filter controls, card detail view,

- Backend: cards array and GET /api/state.
- Rules: cards have aggregate stock, active status, category, prices, reward

Wallet Balance:

- Frontend: Wallet page and dashboard balance cards.
- Backend: users.walletBalance, deposits, transactions, and receipts.
- Rules: Wallet Balance is used for card purchases and is separate from
  Redeemed Balance.

Wallet top-ups:

- Frontend: deposit/top-up sheet.
- Backend: POST /api/deposits, Site B, Paystack, signed callbacks.
- Data: deposits, Site B payment transactions, transactions, receipts.

- Backend: POST /api/purchases.

Daily purchase limits:

- Backend: dailyPurchaseCounts and purchase validation.
- Rule: maximum two purchases per exact USD price per Ghana calendar day.

- Frontend: Redeem page and post-purchase code reveal flow.

Redeemed Balance:

Withdrawal methods:

KYC:

D. AUTHENTICATION & ROLES
--------------------------

FACT FOUND IN PROJECT

User authentication:

- Passwords are hashed using crypto.scrypt.
- Sessions are stored in the sessions array.
- Session tokens are random 32-byte values.
- The cookie is named phantom_session.
- Cookie attributes include HttpOnly, SameSite=Lax, Path=/, and approximately
  30 days of Max-Age.
- requireUser() checks the cookie, session expiry, and referenced user.
- Password and withdrawal PIN hashes are separate.
- Password reset tokens are SHA-256 hashed before storage.
- No mail provider is configured. In non-production mode, the reset token is
  returned in the API response for testing.

Roles and authorization:

- No role field exists on users.
- No admin user table exists.
- No staff or moderator roles exist.
- No permission model exists.
- No admin session system exists.
- No protected admin frontend route exists.
- No general admin read API exists.

Partial admin authorization:

The environment variable ADMIN_APPROVAL_TOKEN is accepted through either:

- x-admin-token
- Authorization: Bearer ...

It is used only for:

- Approving withdrawals.
- Rejecting withdrawals.
- Verifying KYC.
- Rejecting KYC.

The local .env key list does not contain ADMIN_APPROVAL_TOKEN. Therefore the
partial admin routes are expected to return configuration/authentication
failures in the current local configuration.

RECOMMENDATION / INFERENCE

A future dashboard must not use ADMIN_APPROVAL_TOKEN as the final admin
authentication architecture.

It needs:

- Dedicated admin authentication.
- Admin sessions or short-lived tokens.
- Admin/staff roles.
- Fine-grained permissions.
- Session revocation.
- MFA for high-risk actions.
- Separation between viewing, reviewing, approving, and financial operations.
- Audit records for every administrative action.

F. FINANCIAL FLOWS
------------------

1. Wallet Balance top-up
------------------------

FACT FOUND IN PROJECT

Flow:

User
  -> Site A POST /api/deposits
  -> Site A creates PENDING deposit
  -> Site A calls Site B /api/v1/payments/initialize
  -> Site B validates signed request
  -> Site B calls Paystack transaction initialize
  -> User completes Paystack checkout
  -> Paystack webhook reaches Site B
  -> Site B verifies raw-body HMAC-SHA512
  -> Site B verifies/reconciles payment
  -> Site B sends signed callback to Site A
  -> Site A reconciles callback
  -> Site A credits Wallet Balance

Site A creates a deposit containing:

- Amount and minor-unit amount.
- Currency.
- Purpose WALLET_TOPUP.
- Site A transaction ID.
- Local reference.
- Expiry.
- Callback ID storage.
- Payment provider fields.

Site B stores a payment transaction with:

- Its own transaction ID.
- Paystack reference.
- Amount in minor units.
- Purpose.
- Status such as PENDING, SUCCESS, or FAILED.
- Expiry and callback details.

Wallet credit occurs in completeDeposit() only when:

- The callback is signed.
- The user ID matches.
- Amount and currency match.
- The Paystack reference is valid.
- The callback status is successful.
- The deposit is not already successful.
- The deposit has not expired.

When credited, Site A creates:

- A wallet credit transaction.
- A wallet deposit receipt.
- A new Wallet Balance amount.

Duplicate prevention:

- Deposit status SUCCESS prevents re-crediting.
- Callback request IDs are stored.
- Transaction and receipt creation is reference-idempotent.

2. Card purchase
----------------

FACT FOUND IN PROJECT

Flow:

User
  -> selects card
  -> POST /api/purchases
  -> backend checks session
  -> validates idempotency key
  -> checks card stock and active status
  -> checks minimum Wallet Balance
  -> checks available Wallet Balance
  -> checks daily price limit
  -> debits Wallet Balance
  -> decrements aggregate card stock
  -> creates purchase/order
  -> creates sealed redeem code
  -> creates wallet debit transaction
  -> creates purchase receipt

Purchase restrictions:

- Valid idempotency key required.
- Card must be active and have stock.
- Wallet Balance must be at least GHS 30.
- Wallet Balance must cover the card price.
- Maximum two purchases per exact USD price per Ghana calendar day.
- Purchase mutation is serialized within the Node process.
- Same idempotency key cannot be reused for another card.

The generated code is stored, but ordinary state responses hide it. The
customer must call POST /api/purchases/:purchaseId/code to reveal it.

3. Card redemption
------------------

FACT FOUND IN PROJECT

Flow:

User enters code
  -> POST /api/redemptions
  -> normalize and validate code pattern
  -> locate code
  -> verify code belongs to current user
  -> verify code status is unused
  -> resolve card and purchase
  -> calculate or preserve reward amount
  -> mark code redeemed
  -> assign redemption reference
  -> credit Redeemed Balance
  -> create redeemed transaction
  -> create redemption receipt

Rules:

- Code format is 14 characters.
- Code must belong to the current user.
- Code cannot be redeemed twice.
- Reward multiplier range is currently 3.52 to 4.42.
- Redeemed Balance receives the reward amount, not the purchase price.
- Redeemed history contains the redemption reference.

4. Withdrawal
------------

FACT FOUND IN PROJECT

Flow:

Redeemed Balance
  -> user submits withdrawal
  -> eligibility checks
  -> 10% operational charge calculated
  -> requested amount debited/held
  -> withdrawal record created
  -> transaction and receipt created
  -> KYC review or bypass path
  -> admin approval or rejection

Eligibility:

- At least three lifetime redeemed cards.
- Minimum withdrawal of GHS 10.
- Requested amount cannot exceed Redeemed Balance.
- A saved withdrawal method is required.
- Correct four-digit withdrawal PIN is required.

Charge calculation:

operationalCharge = requestedAmount * 0.10
actualAmount = requestedAmount - operationalCharge

The 10% charge is calculated in POST /api/withdrawals and normalized in
normalizeWithdrawalRecord().

When submitted:

- Redeemed Balance is reduced by the full requested amount.
- The withdrawal record stores requested amount, charge, and actual payout.
- The withdrawal transaction is a redeemed debit.
- The transaction status is pending or PENDING_KYC_VERIFICATION.

KYC paths:

- Verified user: withdrawal starts as pending.
- Unverified user: withdrawal starts as PENDING_KYC_VERIFICATION.
- KYC submission changes the user to PENDING.
- Admin KYC verification releases that user’s KYC-blocked withdrawals to
  pending.
- Admin KYC rejection changes user KYC state to REJECTED.
- GHS 70 bypass payment is processed through Site B.
- Successful bypass payment auto-approves only the linked withdrawal.
- The GHS 70 fee is represented as an external debit and separate external
  refund history entry.

Existing admin withdrawal operations:

- Approve pending withdrawal.
- Reject pending, pending-KYC, or approved withdrawal, subject to
  bypass-payment checks.
- Rejection returns the requested amount to Redeemed Balance.
- Approval changes withdrawal, transaction, and receipt status to approved.

There is no complete payout-provider flow. The application does not currently
show a backend operation that sends approved withdrawals to a mobile-money
provider or records a payout reference.

RECOMMENDATION / INFERENCE

The admin UI should initially treat approval as a controlled workflow state
transition, not as proof that money was actually paid.

A future payout workflow needs separate states such as:

pending_review
approved
processing
paid
failed
reversed
rejected

It must store the payout provider reference and actual provider response.

L. FINANCIAL/SECURITY RISKS
----------------------------

FACT FOUND IN PROJECT

Wallet credit:

- Only completeDeposit() credits Wallet Balance.
- It requires a reconciled signed Site B callback.
- It checks amount, currency, user, purpose, expiry, and duplicate state.

Wallet debit:

- Card purchases debit Wallet Balance.
- The balance helper prevents negative values.
- Purchase idempotency and a serialized mutation queue reduce duplicate debits.

Redeemed Balance credit:

- Redemption marks a code redeemed and credits Redeemed Balance.
- There is no general admin credit endpoint.

Withdrawal debit:

- The full requested amount is deducted immediately when the withdrawal is
  created.
- The transaction remains held through pending/approved/processing-like
  states.
- Rejection returns the requested amount.

Charges:

- The 10% operational charge is stored on the withdrawal and related
  transaction/receipt metadata.
- It is not separately credited to an operational-revenue account.

Payment confirmation:

- Site B validates Paystack webhooks with raw-body HMAC-SHA512.
- Site A validates Site B callbacks with bearer authentication, HMAC-SHA256,
  timestamp, and request ID.
- Payment metadata and amount/currency are reconciled.

Refunds/reversals:

- General refunds are not supported.
- KYC bypass refunds are represented as external transaction, receipt, and
  withdrawal-history records.
- Legacy refund records are normalized to avoid re-crediting Redeemed Balance.

Duplicate prevention:

- Deposit callbacks use callback request IDs and successful status checks.
- Transactions and receipts are reference-idempotent.
- Purchases use idempotency keys.
- Site B deduplicates Paystack webhook event IDs.

Audit trail:

- No persistent admin audit trail exists.
- Transaction and receipt records are financial history, not actor/action
  audit records.
- Console logging is not a durable audit trail.

DANGEROUS ADMIN UI BEHAVIOR THAT MUST BE PROHIBITED

The future UI must not allow direct editing of:

- users.walletBalance.
- users.redeemedBalance.
- Successful deposit statuses.
- Paystack references.
- Callback request IDs.
- Transaction amounts.
- Historical transaction references.
- Redemption reward amounts after redemption.
- Withdrawal requested amounts after creation.
- Operational charge calculations.
- KYC payment success state.
- Site B payment status.
- Refund linkage.

Any correction must be implemented as an explicit compensating transaction or
controlled workflow, never by editing historical records.

RECOMMENDATION / INFERENCE

The safest first admin dashboard is largely read-only, with only the existing
withdrawal/KYC actions exposed after stronger authorization and auditing are
added.

P. INCOMPLETE OR SUSPICIOUS CODE
--------------------------------

FACT FOUND IN PROJECT

1. Frontend duplication

index.html contains a large legacy mock-data implementation while app.js
supplies newer API-backed behavior. Both define overlapping renderers and
handlers.

2. Mock data remains in production page code

index.html contains random card, transaction, method, and code generators
using Math.random().

3. Legacy global overrides

app.js captures and replaces functions such as renderAll, renderDashboard,
renderTransactionList, and other global handlers.

4. Logout duplication

Both the legacy inline code and app.js define logout behavior. The API-backed
version is authoritative when loaded, but the duplication is risky.

5. Contact form has no backend

The UI presents a contact form, but there is no contact endpoint or storage
model.

6. Notifications are unfinished

The Settings page says notification preferences are coming soon.

7. Withdrawal lifecycle is incomplete

Constants include processing, completed, and cancelled, but there is no
complete admin API for transitioning payouts through those states.

8. No payout provider integration

Approved withdrawals do not have a payout provider reference or provider
response.

9. No KYC review endpoint for documents

KYC documents are stored on disk, but no admin document retrieval route exists.

10. No persistent audit log

Console messages are not durable audit records.

11. Site B is minified into one line

payment-service/server.js is difficult to inspect and maintain because nearly
the entire implementation is on one line.

12. Data appears development/test-heavy

The persisted snapshot contains local-test payment reasons, test-like users,
mixed historical statuses, and several records with incomplete lifecycle
fields.

13. Current snapshot inconsistency

The current data contains 80 purchases and 80 codes, with all codes marked
redeemed, while all purchases still have status sealed. This may be a
legacy-state inconsistency or a deliberate historical representation, but it
should be investigated before relying on status counts.

14. Missing admin environment configuration

ADMIN_APPROVAL_TOKEN exists in .env.example but not in the local .env key list.

15. Password reset development behavior

In non-production mode, the password reset token is returned in the API
response because no email provider exists.

16. Hard-coded Paystack email assignments

The allowed payment email addresses are hard-coded in payment-config.js.

RECOMMENDATION / INFERENCE

The admin implementation should not attempt to clean up these issues as part
of the UI task. They should be documented, tested, and handled as separate
backend work.

The current application has:

- One main Site A process.
- One payment-service process.
- JSON file persistence.
- Four partial admin mutation endpoints.
- No admin UI.
- No role system.
- No audit system.

RECOMMENDATION / INFERENCE

Recommended architecture:

Admin browser
    -> Dedicated admin frontend
    -> Dedicated /api/admin/* backend layer
    -> Admin authentication and permission middleware
    -> Domain services
    -> Site A data store or future database
    -> Site B only for payment reconciliation

Recommended backend boundaries:

- admin-auth
- admin-users
- admin-withdrawals
- admin-kyc
- admin-deposits
- admin-transactions
- admin-cards
- admin-audit

The admin UI should use backend-provided view models rather than reading raw
JSON or reconstructing relationships in the browser.

S. IMPORTANT NOTES FOR THE DESIGNER/DEVELOPER
----------------------------------------------

FACT FOUND IN PROJECT

- No admin dashboard was built during this audit.
- No project files, database files, migrations, authentication logic, or
  financial logic were modified.
- No Paystack or Site B behavior was changed.
- Existing automated tests passed.
- The current user-side theme is warm, mobile-first, and customer-oriented.

  separate.

RECOMMENDATION / INFERENCE

The admin dashboard should be designed as a controlled operations and
reconciliation system:

- Read broadly.
- Mutate narrowly.
- Never directly edit balances or historical financial records.
- Require explicit reasons for financial actions.
- Show all linked references.
- Preserve Site B payment isolation.
- Add audit logging before expanding admin powers.
- Treat current data inconsistencies as migration/reconciliation questions,
  not UI problems.
